# Synology не видит ИБП: диагностика USB UPS Server

[На главную](../README.ru.md) · [Установка](INSTALL.ru.md) · [English](TROUBLESHOOTING.md)

Проверяйте цепочку по порядку: **USB в системе → права → драйвер → свежие
показания NUT → подключение DSM → проверка безопасного останова**.
Ошибка на раннем шаге не исправляется настройкой следующего.

## Пакет не поддерживается на платформе Synology NAS

Эта ошибка появляется до запуска приложения. Проверьте процессор NAS и выбранный
SPK: DS423 с RTD1619B использует `aarch64.spk` с внутренним `arch="armv8"`;
Intel/AMD NAS — `x86_64.spk`. Не путайте DS423 с DS423+: это разные платформы.
Пакет рассчитан на DSM 7.2.2 и выше. Переименование файла SPK не меняет его
архитектуру. В сообщении об ошибке укажите точную версию пакета, DSM и модель NAS.

## ИБП нет в списке USB

1. Обновите список в настройках приложения. Переподключите USB-кабель, проверьте
   другой разъём и кабель передачи данных. Выходы питания ИБП не отключайте.
2. В собственной SSH-сессии на NAS выполните:

   ```sh
   sh /var/packages/usb-ups-server/target/tools/collect-dsm.sh
   sudo dmesg | tail -n 80
   ```

3. Если VID:PID ИБП нет и в системной диагностике, приложение ещё не может
   открыть устройство. Ищите причину в кабеле, USB-контроллере или драйвере ядра.
   Перебор NUT-драйверов и смена прав этого не исправляют.

`error -110` в журнале ядра означает тайм-аут USB, но сам по себе не доказывает
конкретную причину. Сопоставьте время и USB-порт с подключением именно ИБП.
Не считайте загрузочную USB-флешку устройством ИБП.

## Нет доступа к USB

Если устройство есть, но журнал сообщает `Permission denied` / `Access denied`,
назначьте доступ только для его VID:PID. Пример для `0925:1234`:

```sh
sudo sh /var/packages/usb-ups-server/target/tools/usb-access.sh install-rule 0925 1234
```

Переподключите USB. Если helper сообщает о недоступном udev, приложите его
полный вывод и системную диагностику. Каталог `/etc/udev/rules.d` создаётся helper-скриптом при установке правила.

`grant` выдаёт временный ACL, если в DSM есть `setfacl`; после переподключения
его нужно повторить. Не выдавайте общий доступ ко всем USB-устройствам.

## RICHCOMM 0925:1234: Entity not found

На проверенном «UPS USB Mon V2.0» строка производителя RICHCOMM не означает,
что нужен `richcomm_usb`. Рабочий профиль:

```text
driver: nutdrv_qx
subdriver: armac
vendor_id: 0925
product_id: 1234
serial: пусто
```

У этого экземпляра USB-серийный номер ненадёжен; профиль приложения оставляет его
пустым. Для других моделей/ревизий сверяйтесь с выводом подбора и журналом.
Не подменяйте USB ID, чтобы заставить неподходящий драйвер открыть устройство.

## Device busy, Resource busy, драйвер не запускается

Один ИБП может уже использовать штатный USB-драйвер DSM, другой пакет, контейнер
или второй NUT. Посмотрите процессы и порты в системной диагностике. Сначала
определите владельца устройства; затем спланируйте переключение мониторинга.

Ошибка `Address already in use` относится к порту сервера, а не USB: проверьте,
какой процесс слушает `3493`. Для первичного чтения можно временно использовать
`3494`, но штатному клиенту DSM обычно нужен `3493`.

## DSM не подключается к серверу ИБП

Если показания приложения свежие:

- В DSM выберите **Сервер ИБП Synology** и IP компьютера, где работает наш NUT.
  Для нативного пакета на том же NAS используйте собственный LAN-IP NAS.
- Адрес прослушивания приложения должен принимать запросы на этот IP.
  `127.0.0.1` не принимает подключения по LAN-IP. `0.0.0.0` слушает все IPv4-интерфейсы,
  а не является адресом, который нужно вводить в DSM как адрес сервера.
- На проверенной DSM 7.2.2 поле сервера отвергает `127.0.0.1`; LAN-IP принимается.
- Порт — `3493`, имя ИБП — `ups`, монитор — `monuser` / `secret`.
- Разрешите TCP 3493 только нужным клиентам в брандмауэре. Не отключайте
  брандмауэр целиком и не пробрасывайте NUT в интернет.

С машины, где установлен NUT-клиент:

```sh
upsc ups@SERVER_IP:3493
```

Замените `SERVER_IP` реальным IP. В DSM `upsc` может находиться в
`/usr/syno/bin/upsc`. Доступность показаний через `upsc` подтверждает ответ NUT,
но не доказывает, что DSM уже настроена на безопасный останов.

## Нет заряда батареи или времени работы

У простых Q1/Megatec-устройств могут отсутствовать `battery.charge` и
`battery.runtime`. Проверенный RICHCOMM сообщает напряжение батареи, но не
заряд в процентах и не оставшееся время. Приложение не вычисляет эти значения
из напряжения. Если напряжение, нагрузка и время опроса обновляются, отсутствие
процента само по себе не является ошибкой связи.

## Пустое окно или ошибка сессии DSM

Закройте старое окно приложения, обновите страницу DSM через HTTPS и откройте
приложение из главного меню. Нужна текущая сессия администратора DSM.

Приложение использует текущую сессию администратора DSM. Если она истекла,
войдите в DSM заново и откройте приложение.
Если ошибка остаётся, укажите точную версию пакета и сообщение. Ключ запасного
интерфейса на 8787 не нужен для окна DSM и не заменяет сессию DSM.

## Xpenology N40L и OHCI

На первом AMD N40L контроллеры OHCI `1002:4397` не имели драйвера. EHCI работал,
но этого не хватало для появления ИБП. Это особенность проверенной конфигурации
Xpenology, а не обязательная настройка для всех Synology.

Команды чтения:

```sh
uname -r
lsmod | grep -Ei 'ohci|ehci|uhci'
lspci -nnk | grep -A 3 -i 'USB controller'
modinfo ehci-pci | grep -E 'filename|vermagic'
grep '^unique=' /etc.defaults/synoinfo.conf
```

Поддержка `lspci` и `modinfo` зависит от системы. Сообщение
`Module ohci-pci not found` означает, что нужного модуля нет в текущей системе.
Не загружайте произвольный `.ko` только по совпадению `uname -r`: нужна совместимость
платформы, сборки ядра и символов.

Для **broadwellnk / DSM 7.2 / 4.4.302+** есть отдельная
[инструкция сборки и временного теста OHCI](../dsm/kernel/ohci/README.ru.md).
Эти модули не входят в SPK. На первом NAS они загружены временно; постоянная
загрузка через Arc и восстановление после перезагрузки ещё не проверены.

## Что приложить к сообщению

1. Модель ИБП, USB VID:PID и описание симптома.
2. Модель/процессор NAS, точную версию DSM, версию приложения, SPK или Docker.
3. **Журнал → Скачать диагностику**. Если окно недоступно:

   ```sh
   sh /var/packages/usb-ups-server/target/tools/collect-dsm.sh
   sudo tail -n 100 /var/packages/usb-ups-server/var/service.log
   sudo tail -n 100 /var/packages/usb-ups-server/var/nut.log
   ```

4. Что изменилось перед ошибкой: обновление, USB-порт, кабель, перезагрузка,
   настройки драйвера или другой пакет ИБП.

Команда сбора системы выполняет чтение. Диагностика может содержать IP, USB-серийный
номер, модель оборудования и журналы. Перед публичной публикацией просмотрите
её и удалите личные сведения. **Не прикладывайте `admin-token`, cookie DSM,
SynoToken, `server.key`, пароли и полный каталог данных пакета.**
